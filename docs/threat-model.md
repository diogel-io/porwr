diogel-io/workspace#142 restricted relays to `wss:` and loopback `ws:`, gave Blossom uploads a

diogel-io/workspace#148 added the "Load remote images" setting, kept in the protected store. With it

rows for T29 and T32 and sections 7 and 8 describe the code after that change.

diogel-io/porwr#375 (diogel-io/porwr#374) made signing a NIP-04 direct message (kind 4) an elevated

diogel-io/porwr#373 deleted an unused export of the session key, closed the wallet relay connections
on lock, refused a malformed NIP-04 or NIP-44 counterparty before queueing it, and allowed only

diogel-io/porwr#372 bounded the approval queue at 5 pending requests per site and 20 in total,
refusing rather than evicting, and refused oversized page payloads before they reach a handler
(ADR D18). The row for T38 describes the code after that change.

## How to read and maintain this document

- A pull request that adds an asset, a trust boundary, or a control, or that changes one listed
  here, updates this document in the same pull request. The security review checklist in
  [SECURITY.md](../SECURITY.md) applies to every change touching a
  security-sensitive path.
- Paths are cited as they exist at the baseline commit, or, for a row changed later, after the change
  named under "Changes since the baseline". A pull request that changes a control adds itself to
  that list. When the baseline moves, re-verify every row and clear the list.
- **Disclosure rule.** This repository is public. A closed finding is described in full. An open
  finding that could be exploited is given a one-line summary and a tracking reference only; its
  details are held in a private GitHub security advisory on `diogel-io/porwr` and in the private
  workspace issue, and are published here once a fixed version is released. Report suspected
  vulnerabilities privately, never in a public issue: as described in
  [SECURITY.md](../SECURITY.md).

## Scope and method

Porwr is a Manifest V3 browser extension built for Chrome (service worker background, side panel)
and Firefox 115+ (event page background, `sidebar_action`). Both builds share the code at the
baseline commit; target-specific behaviour is noted where it matters.

The model covers everything in the extension: the `window.nostr` and `window.webln` page surface,
approval and grants, the vault and its cryptography, key generation, import and export, backups,
auto-lock, NIP-17 messaging, relay transport, the NIP-47 wallet connection, Blossom uploads, remote
content loaded by Porwr's own pages (profile images, relay icons, NIP-05 lookups), local logs and
history, the manifest, and the build and release supply chain.

It was built by reading the paths named in each row at the baseline commit and the tests that
exercise them. It does not defend against an attacker who already controls the operating system,
the browser binary, or the user's unlocked browser profile with developer tools or debugger access.

## 2. Trust boundaries

| #   | Boundary                                                               | Enforcement at the baseline                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| --- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| B1  | Web page ↔ injected provider                                           | `window.postMessage` with `event.source === window`, same-origin, and shape checks (`src-bex/window-message-security.ts`, `src-bex/window-message-handler.ts`). Only methods in `PAGE_METHOD_TO_ACTION` (`src-bex/page-actions.ts`) are forwarded, and no origin is sent                                                                                                                                                                                                                                                                                                                                      |
| B2  | Content script ↔ background over `porwr:page`                          | The requesting site comes only from the port's browser-supplied sender: `sender.origin` on Chromium, the origin of `sender.url` on Firefox (`pageOriginOf` in `src-bex/services/sender-policy.ts`). `src-bex/services/page-channel.ts` strips `origin` and `approved` from payloads, refuses a sender that names no http(s) site, and serves only the page allowlist                                                                                                                                                                                                                                          |
| B3  | Background ↔ Porwr's own pages (panel, dashboard)                      | The raw `chrome.runtime.onMessage` listener accepts only senders classified `extension-page` and refuses every origin-scoped action from them (`classifySender` in `sender-policy.ts`, `decideRouting` in `src-bex/services/message-routing.ts`). The Quasar bridge serves only `ping`. The panel is untrusted for lifecycle purposes and decides only against a request id (D1, D5)                                                                                                                                                                                                                          |
| B4  | Background ↔ storage                                                   | Vault encryption at rest; `chrome.storage.session` restricted to trusted contexts (`lockDownSessionStorage`); queue persistence limited to metadata (D6); grants, bindings, and auto-lock state kept in the extension's own IndexedDB, which content scripts cannot open, and moved out of `chrome.storage.local` once at startup (`src-bex/services/protected-storage-migration.ts`)                                                                                                                                                                                                                         |
| B5  | Extension ↔ relays, Blossom servers, wallets                           | Relay URLs normalised by `src/services/relay-url.ts`; NIP-42 AUTH signs only kind 22242 (`src-bex/services/relay-auth.ts`); NIP-47 requests are signed with the connection's own client key, never the user's Nostr key (`src-bex/services/nip47-client.ts`)                                                                                                                                                                                                                                                                                                                                                  |
| B6  | Extension ↔ browser panel APIs                                         | The panel opens only from the toolbar gesture (`src-bex/services/panel-surface.ts`, `action.onClicked` in `background.ts`); no approval popup or automatic opening exists (D3, D4, D17)                                                                                                                                                                                                                                                                                                                                                                                                                       |
| B7  | Porwr's own pages ↔ remote content hosts                               | Profile images, relay icons from NIP-11 metadata (`src/components/dashboard/RelayBrowserModal.vue`), and NIP-05 documents are fetched by extension pages, never by the background on a site's behalf. `ProfileView` renders only when no request is shown (`src/pages/sidebar/SidebarHome.vue`), and NIP-05 lookups run only on a user action (`src/services/nip05-service.ts`, `src/services/contact-list-service.ts`). The manifest holds no host permissions                                                                                                                                               |
| B8  | Content script on a wallet page ↔ background over `porwr:wallet-relay` | Firefox only (workspace#85). The background arms the content script only in the tab it opened for a pending wallet authorization, by `tabs.sendMessage` to that tab's top frame. The relay port is accepted only from that tab's top frame, at the pending authorization's exact origin, per the browser-supplied `sender`, and carries one message of public connection details, which are then checked as any `nwc:success` is (`src-bex/services/wallet-connect-popup.ts`, `handleNip47AuthorizationRelay` in `src-bex/handlers/nip47.ts`). The general runtime channel still refuses content scripts (B3) |

B2 is the load-bearing boundary for the page surface. The content script declares no `all_frames`
(`src-bex/manifest.json`), so the provider runs in top-level documents only and a third-party iframe
cannot raise a request under the embedding site's origin.

## 3. Adversaries

| #   | Adversary                                          | Capability assumed                                                                                                                                                               |
| --- | -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A1  | Malicious or compromised website                   | Calls every allowlisted `window.nostr` and `window.webln` method at any rate, with crafted content; may hold grants the user gave earlier                                        |
| A2  | Third-party iframe or embedded script              | Runs inside a page the user trusts, in a subframe or in the top frame through an included script                                                                                 |
| A3  | Another extension                                  | Can message Porwr through `chrome.runtime` and inject into the same pages; has no debugger access                                                                                |
| A4  | Malicious relay, Blossom server, or wallet service | Observes what Porwr sends, returns crafted events and responses, requests NIP-42 AUTH; a wallet service sees every payment it is asked to make and controls what it reports back |
| A5  | Local access to the browser profile                | Reads files of a locked profile, or sits at an unlocked browser for a short time; cannot install software                                                                        |
| A6  | Compromised build or dependency                    | Controls a runtime dependency, a build tool, or a CI action                                                                                                                      |
| A7  | Phishing and look-alike origins                    | Controls a domain visually similar to one the user trusts, or persuades the user outside the product                                                                             |
| A8  | Remote content host                                | Serves profile images, relay icons, or NIP-05 documents; observes the user's IP address, the time, and the identity-specific URL requested                                       |

only references are the kind 24133 label and an unused `nip46` field in the NIP-05 response type.
Implementation is tracked in diogel-io/workspace#138. Before it ships, this document must gain a

## 5. Security requirements

These properties hold at the baseline and every change must preserve them. Requirements 1-9 are
carried over from the approval threat model.

1. A signature, encryption, or decryption that a website requests is produced only after an
   explicit user decision on a live request, or under a grant that covers that request type and
   event kind. Signatures Porwr makes for its own features are not website requests and are covered
   by their own threats: relay AUTH (kind 22242, T20), Blossom upload authorisation (T21), and
   direct messages, profile, contact list, and relay list publishing started by the user in Porwr's
   own pages.
2. Unlocking never approves.
3. A request whose live callback is lost can never be approved.
4. An expired request can never be approved, and no setting disables expiry or raises it above the
   compiled ceiling.
5. One request resolves exactly once.
6. The request queue writes no event content, plaintext, ciphertext, invoice, or key material to
   storage.
7. No remote resource is requested as part of an approval.
8. The user sees the requesting origin and the signing account before any approval control.
9. Rejecting is possible in every recoverable state without unlocking first.
10. The requesting origin comes only from the browser-supplied sender, never from a payload.
11. A website reaches only the page allowlist; vault, account, wallet, and decision actions are
    reachable only from Porwr's own pages.
12. A private key leaves the background in plaintext only through `accounts.revealSecret`, to Porwr's
    own pages, after the vault password is given again; an export leaves it only as an `ncryptsec`.
13. A payment is always approved once, and never under a stored grant.
14. Porwr never builds a zap request or fetches an invoice itself.

## 6. Findings

### Closed

**F1 - A public-key grant authorised signing of any event kind.** Closed. At `867eaa6` a stored
grant of kind `-1` meant "no event kind" at the approval call sites and "any kind" in the checker,
so approving a public-key request with "always" authorised signing anything. Grants are now keyed by
request type as well as kind; "no event kind" maps to `null`, not a wildcard (`toPermissionKind` in
`src-bex/services/approval-flow.ts`); a wildcard cannot be created by `grantPermission`, and since
diogel-io/workspace#139 a stored one is never honoured, because it would answer every kind; legacy records are discarded (`src-bex/handlers/permission-handler.ts`). Tests:
`tests/unit/handlers/permission-handler.test.ts` ("does not let a public-key grant authorise
signing", "cannot be created through grantPermission"), `tests/unit/services/approval-flow.test.ts`.

**F2 - Site activity kept the vault unlocked.** Closed. Every bridge handler used to reset the
auto-lock timer. `resetAutoLockTimer` is now called only on `vault.unlock` and `activity.mark`
(`src-bex/dispatcher.ts`), both reachable only from Porwr's own pages. Tests:
`tests/unit/handlers/nip07.test.ts`, `tests/unit/handlers/nip44.test.ts` (assert no reset on site
requests), `tests/unit/services/auto-lock.test.ts`.

**F3 - Approval disclosed the requesting site to a third party.** Closed. The approval screen used to
load a favicon from a Google endpoint. `RequestOriginHeader.vue` now renders the origin string with

Tests: `tests/e2e/approval-network-silence.spec.ts`, `tests/unit/no-remote-resources.test.ts`.

**F4 - Approval responses carried no request identity.** Closed. `nostr.requests.respond` carries a

`tests/unit/services/request-queue.test.ts`, `tests/unit/dispatcher-routing-table.test.ts`,
`tests/e2e/fail-closed.spec.ts`.

**F5 - Some grant and binding limits were enforced only in the UI, or not cleaned up with their
owner.** Closed in diogel-io/workspace#139. The background now refuses a decision duration the risk
class does not allow and the grant store refuses to write or honour one; decrypt requests are
elevated; a site's event kind is validated; a site is bound only on approval; removing an account
removes its grants and bindings; disconnecting a site or removing a wallet removes the matching
WebLN permissions; expired grants are pruned; concurrent decisions cannot both apply; a restarted
worker never restores an overdue key; creating a vault starts auto-lock; and a request is

`tests/e2e/grant-enforcement.spec.ts`.

**F6 - Some security state was stored where it was less protected than it should be.** Closed in
diogel-io/workspace#140. Grants, site bindings, the auto-lock timeout, and the last-activity time
were kept in `chrome.storage.local`, which Porwr's content scripts can read and write, so a
compromised website renderer could have read a user's connected sites, planted a grant, or switched
auto-lock off. They now live in the extension's own IndexedDB, which content scripts cannot open;
existing values are moved once at startup and the old keys deleted; the timeout is clamped and a
future last-activity time counts as now. Tests: `tests/unit/services/protected-storage.test.ts`,
`tests/unit/services/protected-settings.test.ts`, `tests/unit/services/auto-lock.test.ts`,
`tests/e2e/protected-storage.spec.ts`. Tracked in a private security advisory, published with the
fixed release.

**F7 - The per-key export format and the vault password rule were weaker than the vault itself.**
Closed in diogel-io/workspace#141. A per-key export was a zip encrypted with legacy ZipCrypto, which
falls to known-plaintext attacks, around a file with a fixed header and the plaintext nsec; its
entry name was the account alias; and its password, and the vault password, had a minimum only in
the UI. An export is now a NIP-49 `ncryptsec` made in the background with an export password of at
least 8 characters, in a file without the alias; Porwr imports `ncryptsec`, refusing a key that asks
for a scrypt cost above `MAX_NCRYPTSEC_LOGN` (18) before any scrypt runs; the vault password
minimum is enforced in the background; and showing or exporting a key needs the vault password
again. Tests:
`tests/unit/handlers/accounts.test.ts` (including the NIP-49 specification vector),
`tests/unit/handlers/vault-handler.test.ts`, `tests/e2e/accounts.spec.ts`. Tracked in a private
security advisory, published with the fixed release.

**F8 - Relay, Blossom, NIP-47, and remote-content handling lacked the hardening the approval path
has.** Closed in diogel-io/workspace#142. Relays the user configured could use plaintext `ws:`, and
NIP-11 then used `http:`. The Blossom upload authorisation had no `expiration` or `server` tag, a

account switch until the next messaging call. The extension CSP limited neither connections nor
images. Each is now fixed as T19, T21, T22, T24 and T32 describe, and section 8 lists the tests. The
remaining residuals are recorded against those rows and in section 7.

**F9 - Supply-chain and CI controls were incomplete.** Closed in diogel-io/workspace#143. Seven
runtime dependencies nothing imported, and an unused axios boot file, shipped to users with access to
their keys; most workflow actions were pinned to movable tags; workflows ran with write-capable
tokens; nothing proposed dependency updates; secret scanning and push protection were off; and

Test: `tests/unit/workflow-hardening.test.ts`.

**F10 - Several controls lacked a test, and local history had no retention limit.** Closed in

exception history is capped and can be cleared. The background duration-limit test moved to F5
(diogel-io/workspace#139), with the fix it tests.

## 7. Accepted risks

- **Session key across worker restarts (#83, #245).** The unlocked state survives a service-worker
  restart as a non-extractable `CryptoKey` in extension IndexedDB, gated by a session-storage marker
  that the browser clears on exit. A Porwr page can use the key while the vault is unlocked; nothing
  can export it.
- **Logging policy (#87).** Logs record structure, not content. WARN and ERROR messages go to the
  console and the `exceptions` table.
- **No product analytics or telemetry.** Privacy is preferred over rollout measurement.
- **No memory zeroisation.** JavaScript gives no reliable way to erase key bytes; keys are decrypted
  per operation rather than cached in module state.
- **Fingerprinting and lock-state disclosure (T30, T31).** Inherent to NIP-07 as specified.
- **The active account in content-script storage (diogel-io/workspace#140).** `nostr:active` stays
  in `chrome.storage.local`. A compromised page that changed it could only change which account a
  site that has never been approved is offered: the prompt names that account, and a site is bound
  only when the user approves (T2).
- **Release publish script from the workflow's commit (diogel-io/workspace#143).** The Chrome
  publish job runs `.github/scripts/publish-chrome.sh` from the workflow's own commit rather than the
  release tag, so a manual run for an older tag uses the current script. Anyone who can dispatch the
  workflow already controls the workflow file, so taking the script from the tag would add nothing.
- **Extension CSP: remote images over `https:` (T32, diogel-io/workspace#142).** `connect-src` allows
  `'self'`, `https:`, `wss:`, and `ws:` and `http:` to `localhost` and `127.0.0.1`; `img-src` allows `'self'`,
  `data:`, `blob:`, and `https:`. Narrowing `connect-src` to named hosts is not possible, because
  relays, Blossom servers, and NIP-05 hosts are chosen by the user and by the profiles they view.
  Remote profile images therefore load from any `https:` host the user lets them load from; the
  "Load remote images" setting (diogel-io/workspace#148) holds them back until the user asks. It is
  on by default, so a user who has not turned it off keeps the earlier exposure. CSP cannot name an
  IPv6 address, so `[::1]` is not accepted as a loopback relay.
- **The NWC URI in the dashboard page (T22).** The user pastes a connection URI, secret included, into
  the dashboard. Parsing it only in the background would not keep the secret out of that page, which
  already holds what the user typed; the page validates it, sends it once, and clears the field.
- **WebLN `enable` for as long as the user chose (T22, porwr#369).** Once a site is allowed WebLN,
  it can call `getInfo` without a prompt for the duration the user picked: while the page that asked
  stays open for "just this once" (held in background memory, `src-bex/services/webln-session-grants.ts`,
  and cleared on lock), eight hours, or until the user disconnects the site for "always". `getInfo`
  returns only the connection's label and supported methods; every payment still needs its own `once`
  approval (D11).
- **User-disabled auto-lock.** A user may set auto-lock to 0; the protection is then the browser
  session alone.
